검증일: 2026-09-30

## 자동 검증

- 작성, 두 번째 클라이언트 조회, 앱 재생성 후 데이터 유지
- 종목 필터, 최신순, 페이지 이동
- 빈 값·초과 길이·타입 오류·잘못된 운동 종류 거부
- Unicode 길이, 앞뒤 공백 제거
- HTML/SQL 형태의 입력을 데이터로 저장
- 동일 요청 재시도 시 중복 방지 및 다른 내용 재사용 거부
- 없는 게시글, 잘못된 페이지, 교차 출처 요청, 과대 본문 처리
- 4개 작업 스레드의 12개 동시 등록
- 화면 제공, 내부 소스·DB 파일의 웹 노출 차단

JavaScript 문법 검사: community.js / community-api.js 통과.

## 브라우저 검증

실제 전달 DB와 분리한 테스트 DB, 8001번 포트를 사용했습니다.

- 빈 목록 표시 및 빈 입력의 필드별 안내
- 정상 작성 후 성공 안내와 목록 표시
- 상세 조회와 새로고침 후 동일 글 표시
- 플랭크 필터 선택 시 스쿼트 글 제외
- 서버를 실제 중단한 상태에서 저장 실패 안내 및 입력 유지
- 서버 재시작 후 재시도로 정상 저장, 기존 글 유지
- `<img ...>` 입력이 실제 이미지 요소로 생성되지 않고 본문 문자로 표시됨
- localhost와 PC의 Wi-Fi IPv4 주소로 각각 접속해 같은 게시글 조회
- HTTP Wi-Fi 주소로 게시글 등록 성공
- 390px 모바일 크기에서 내용 너비 375px, 가로 넘침 없음

## 기존 코드 유지

moving2.js, dashboard.js, MainStyle.css, style.css는 ZIP 원본과 해시가 같습니다. index.html의 메뉴·섹션·로더와 게시판 화면용 body 클래스만 통합했습니다. 실제 카메라 운동 측정은 수행하지 않았습니다.

## 추가 검증: 동일 Wi-Fi 다중 기기 접속 및 데이터 유지

검증일: 2026-11-04

### 검증 환경

- 실행 브랜치: `Feature/MVP-Integration`
- 서버: Windows 노트북, Flask + Waitress
- 실행 명령어: `python main.py`
- 클라이언트: 스마트폰
- 네트워크: 부경대학교 `eduroam`
- Windows 네트워크 프로필: Public
- 서버 Wi-Fi IPv4: `172.18.132.207`
- 게시글 DB: `instance/community.sqlite3`

### 수동 검증 결과

| 노트북에서 로컬 서버 접속 | PASS |

| 서버 재시작 후 기존 게시글 유지 | PASS |

### 검증 결과 분석

기존 접속 테스트에서 실제 Wi-Fi IPv4 주소가 아닌 다른 LAN 후보 주소를 사용하여 접속에 실패한 사례가 있었습니다.

`ipconfig`로 실제 Wi-Fi 어댑터의 IPv4 주소를 확인한 후 스마트폰에서 서버에 정상적으로 접속할 수 있었습니다.

서로 다른 기기에서 작성한 게시글을 양쪽에서 조회할 수 있었으며, 서버 재시작 후에도 기존 게시글이 유지되었습니다.

따라서 이번 테스트 환경에서 LAN 접속, 공통 SQLite 데이터베이스를 통한 게시글 공유, 데이터 영속성이 정상 동작함을 확인했습니다.

서버 코드 수정이나 신규 Windows 방화벽 허용 규칙은 필요하지 않았습니다.
